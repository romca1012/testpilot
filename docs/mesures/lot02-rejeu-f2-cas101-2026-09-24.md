# F2 — rejeu du cas 101, tirage 1 (2026-09-24)

**Objet.** À la mesure de base du lot 12, le tirage 1 du cas 101 avait été classé `non_conforme` parce que
l'agent avait inventé, dans le Contexte, l'affirmation `le module Odoo "pilote_p1_c101_i1_20260923" est
installé et actif` (assertion d'ENVIRONNEMENT, jamais un constat sur l'application). La campagne « après »
du lot 12 a ensuite régénéré ce cas sans l'inventer (`conforme`) : le rejeu d'un NOUVEAU tirage ne peut donc
pas prouver le correctif. On rejoue la version **exacte** de la base.

**Protocole.** Le `.feature` et les steps de `lot12-base-20260924/campagne.json` (cas 101, tirage 1, module
`pilote_p1_c101_i1_20260923`) sont rejoués par `BehaveRunner` + `Executor` contre l'instance locale
(`localhost:10017`), sur une **copie** des données (jamais `data/` du poste, clé de chiffrement lue à la
source et passée par l'environnement). Aucun appel LLM. Le scénario échoue dans le Contexte, avant toute
action : aucune écriture sur l'instance. Deux passages, même version, deux codes :

| | Code | Axe exécution | Axe fonctionnel | Statut de lecture | Cause | Step en échec |
|---|---|---|---|---|---|---|
| **Avant** | lot 12 final (`master` = `4f2f9de`) | `success` | **`non_conforme`** | `failed` | `assertion_mismatch` | `ASSERT FAILED: Le module Odoo 'pilote_p1_c101_i1_20260923' n'est pas installé.` |
| **Après** | lot 02 | **`blocked`** | `indetermine` | **`blocked`** | `precondition_non_remplie` | type `given` — `PreconditionNonRemplieError: Le module Odoo 'pilote_p1_c101_i1_20260923' n'est pas installé.` |

Le tirage passe de « défaut applicatif présumé » à « bloqué : prérequis d'environnement non rempli », sans
changer une ligne de la version rejouée. L'application n'est plus accusée d'un prérequis que l'agent avait
inventé.

**Ce que le rejeu a aussi révélé (défaut de la migration 48, corrigé avant ce rapport).** Le premier essai
« après » a échoué sur la copie de la vraie base (`user_version` 47) : `table "execution" already exists`.
Les tables d'une base réelle s'écrivent `CREATE TABLE "execution"` (guillemets ajoutés par SQLite après
`ALTER TABLE … RENAME`), ce que les bases neuves des tests ne montraient pas. Un second essai a échoué sur
une violation de clé étrangère PRÉEXISTANTE et sans rapport (`project_member` → utilisateur supprimé) que la
migration prenait pour un dégât de la reconstruction. Les deux sont corrigés et couverts par des tests qui
échouent sans correctif ; vérifié sur la copie de la vraie base : 31 tables, lignes identiques avant/après,
`integrity_check` ok, aucune violation nouvelle.
