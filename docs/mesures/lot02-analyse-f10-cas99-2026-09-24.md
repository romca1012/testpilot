# F10 — cas 99 : analyse du « refus silencieux » (2026-09-24)

Analyse SANS correctif, demandée avant tout code. Source : campagne du lot 12 (base et « après »),
6 tirages du cas 99 (`/retenue_garantie/1` sauf le tirage 1 « après » : `/retenue_garantie/2`), les
artefacts d'exécution (trace Playwright, JSON Behave) et le journal de l'instance Odoo locale
(`repo_v17-odoo17-1`).

a observé ne permet de trancher.

## Pourquoi l'outil a dit « refus silencieux »

Le message d'échec du cas 99 affirme : « NI la page NI le serveur n'ont donné de raison lisible ».
C'est **faux dans les deux moitiés** — c'est un trou d'observation, pas un silence :

1. **Le serveur a répondu, et l'outil ne l'a pas retenu.** `environment._capturer_reponse_formulaire`
   ne garde que `response.json()` ; sur une réponse HTML (500) l'appel lève, l'exception est avalée
   (`except Exception: pass`) et `context.reponse_formulaire` reste `None`. Le **code HTTP 500** —
   un signal produit par le runtime, pas par l'agent — n'est jamais stocké.
2. **La page a affiché une raison, hors des sélecteurs surveillés.** `_SELECTEURS_ERREUR`
   (`.alert-danger`, `[role='alert']`, `.invalid-feedback`, `.o_has_error .text-danger`…) ne contient ni
   `#s_website_form_result` ni `.text-danger` seul : le texte rouge n'est pas vu.
3. Résultat : `_refus_serveur` rend `None`, `diagnostic_soumission` rend « REFUS SILENCIEUX », et
   `check_count_increased_by_one` lève quand même une `AssertionError` → `ASSERT FAILED` →
   `non_conforme`, alors que le message joint dit lui-même « l'outil NE conclut PAS à un défaut ».
   **Le statut affirme ce que le message refuse d'affirmer** (F10, faux `non_conforme` I2).

## Est-ce l'arbitrage du 2026-07-23 qui est en cause ?

L'arbitrage (« un refus serveur GÉNÉRIQUE, sans champ nommé, sur une saisie valide côté navigateur =
défaut de comportement de l'application → `non_conforme` ») s'applique à `_refus_serveur` quand une
réponse JSON `{"error": …}` est **captée**. Ici la branche n'a jamais été atteinte : la réponse n'a pas
été captée. Le cas 99 est donc **tombé dans le repli final** (« silence total »), qui produit le même
statut `non_conforme` par le seul `raise AssertionError`, sans que l'arbitrage l'ait décidé.
**L'arbitrage n'est pas contredit ; il n'a pas été appliqué. Mais le réutiliser tel quel pour une
réponse HTTP 500 étend son périmètre : c'est ta décision.**

## Proposition (rien n'est codé)

**A. Corriger l'observation — sans toucher au verdict** (aucune décision requise) :
capturer, pour toute réponse à `/website/form/…`, le **code HTTP** et le type de contenu (pas
seulement le JSON) ; ajouter `#s_website_form_result` aux sélecteurs d'erreur. Le message dit alors
la vérité : « le serveur a répondu HTTP 500 (erreur interne) ; la page affiche : « An error has
occured… » ». Ce sont des signaux du runtime, jamais un texte de l'agent (décision 0015).

**B. Décider comment classer les trois cas que A rend distincts** — c'est ici que ton arbitrage
intervient :

| Situation observée | Aujourd'hui | Proposition |
|---|---|---|
| Réponse JSON d'erreur **générique** (`{"error": …}`), saisie valide | `non_conforme` (arbitrage 07-23) | **inchangé** |
| **HTTP 5xx** (exception non gérée), saisie valide côté navigateur | `non_conforme` par le repli, sans preuve affichée | **Option 1 : `non_conforme` assumé et prouvé** — une exception serveur sur une saisie acceptée est un défaut de robustesse de l'application, même si notre donnée en est le déclencheur (le serveur doit répondre par une validation, pas planter). Cause nouvelle affichée : « erreur interne du serveur (HTTP 5xx) ». **Option 2 : `blocked`** (prérequis d'environnement non rempli, ex. équipe absente) — plus prudent, mais elle range dans l'environnement un défaut qui peut être réel. |
| **Vrai silence** : aucune réponse captée, aucun message, aucun champ invalide | `non_conforme` (repli) | **`indetermine`** (« à instruire »), jamais `non_conforme` ni `conforme` — cause nouvelle « refus non expliqué » (le F10 du plan, D-à ouvrir) |

Ma recommandation : **A + Option 1 + le vrai silence en `indetermine`**. Un HTTP 500 est la preuve
la plus forte qu'un outil de test puisse obtenir d'un défaut côté serveur, et la règle « faux PASSED =
pire défaut possible » plaide contre de le dissimuler en `blocked`. Ce cas 99 précis reste à instruire
côté application (équipe de support absente du formulaire ou de la copie de base).

**À trancher** : (1) 5xx → `non_conforme` (option 1) ou `blocked` (option 2) ? (2) le vrai silence →
`indetermine` avec la nouvelle cause « refus non expliqué » ? Ni l'un ni l'autre n'est codé.
