**Écarts constatés avec le plan**

   « le smoke-check a bloqué avant exécution » est interprété comme « signalé au gate de relecture ».
   Le smoke-check n'est pas appelé dans la boucle de génération ni en qualification : il n'a donc
   pas d'effet sur une campagne automatisée. Limite assumée : un texte figé entièrement en Python
   (jamais passé en paramètre Gherkin) n'est pas vu.
3. F8 : `inspect_page_snapshot` cité par le plan n'existe pas ; seul `attempt_form_submission`
   alimente les messages observés, or il est désactivé par défaut (`calibration_writes_enabled=0`
   sur les deux projets de test). En pratique le registre de messages restera vide sur ces projets
   et TOUT texte de message affirmé sera signalé — voulu, mais bruyant.
4. F9 (ajouté en cours de lot) : le prompt (Règle 3) et le message `TRANSPORT_INTERDIT`
   recommandaient eux-mêmes `search_count([])` ; corrigés. Le refus est bloquant sans que D4 (lot 03,

5. Suite pytest : une erreur `[garde données réelles] … supprimé data/selecteurs/projet-1.jsonl`

## Compléments du 2026-09-24 (revue verdict-reviewer et consignes du porteur)

**F7 — règle exacte codée (`_est_navigation`) et angle mort du fragment levé.** Sur Odoo 16 et
17.0 la navigation du back-office ne change que le fragment (le chemin reste `/web`) : la version
initiale (chemin seul) traitait un clic de menu comme une soumission possible.

| transition d'URL | contrôle exécuté |
|---|---|
| chemin différent (`/en/servicemetiers` → `/en/mutation/67`) | non |
| chemin `/odoo/…` (≥ 17.2) différent | non (comportement conservé) |
| même chemin, `action` / `menu_id` / `model` / `view_type` change (clic de menu, changement de vue) | non |
| même chemin, seule la clé `id` apparaît ou change (sauvegarde Odoo 16/17.0) | **oui** |
| même chemin, fragment identique ou `#` seul (`href="#"` portail) | **oui** |
| URL strictement identique (dialogue, AJAX portail) | **oui** |

Tests (`tests/test_refus_hors_soumission.py`, 10 lignes de table + 3 scénarios `click_button`) :
clic de menu `/web#action=A` → `B` sans contrôle ; sauvegarde `…view_type=form` → `+id=42` avec
contrôle ; dialogue sans changement d'URL sans faux `donnee_invalide` ; chemin `/odoo/…` inchangé.

Sonde réelle sur **Odoo 17.0+e** (staging Sapian, projet 12, helpers réels, aucune trace laissée) :
clic « Nouveau » (liste → formulaire) → navigation, contrôle sauté ; clic sur
`.o_form_button_save` → URL strictement identique avant/après (1,2 s après le clic), contrôle
exécuté. **Non mesuré** : Odoo 16.0 et 17.0 Community, et un refus réel de sauvegarde
back-office → à faire sur le banc du lot 04 avec un scénario Behave complet (consigné au plan §3).
