### Ce que le lot change, en clair

La bibliothèque Odoo ne couvrait que « soumettre un formulaire, vérifier l'enregistrement »
(niveau portail). Un ERP se teste sur des flux de gestion : boutons de workflow, barre d'état,
lignes de commande, assistants, effets en chaîne sur d'autres documents. Ce lot ajoute ce
vocabulaire en quatre sous-lots :

- **08a** — détection de la version Odoo, table de sélecteurs par version, deux helpers d'attente
  et de construction d'URL.
- **08b** — steps de gestion : ouvrir un formulaire par modèle technique, renseigner une relation,
  ajouter une ligne x2many, enregistrer/annuler, cliquer un bouton d'action, valider un
  assistant, lire la barre d'état, filtrer une liste.
- **08c** — effets vérifiés côté serveur (RPC) : état technique, champ numérique avec tolérance de
  devise, documents liés et leur état, rapport PDF généré.
- **08d** — refus d'accès (preuve UI + RPC) et société de travail (multi-société).

### Non vérifié sur banc réel — à faire par le porteur avant de considérer ce lot fiable en production

Aucun démon Docker ni instance Odoo réelle dans ce cloud (`docker ps` échoue). Concrètement :

- **La table de sélecteurs** (`_selecteurs.py`) reprend le texte du lot pour les clés qu'il donne
  explicitement (`bouton_action`, `barre_etat_courante`, `ligne_x2many_ajout`,
  `dialogue_bouton_principal`, `enregistrer`, `indicateur_chargement`) ; pour les six autres
  (`ligne_x2many_cellule`, `dialogue`, `notification_erreur`, `fil_ariane`,
  `recherche_facette`, `ignorer`), elle suit des conventions DOM documentées du web client Odoo,
  **jamais mesurées directement**.
- **`odoo_url_action`** : la forme récente (`/odoo/action-<id>`, ≥ 17.2) est ma meilleure
  compréhension documentée de la convention Odoo — jamais vérifiée contre un vrai serveur 18.0.
- **`step_rapport_pdf_genere`** (08c) et **`step_travailler_dans_la_societe`** (08d) touchent
  l'UI sans le moindre repère mesuré (menu Imprimer, sélecteur de société).
- **Les steps RPC** (08c, 08d) suivent un patron déjà mesuré ailleurs dans le dépôt
  (`_odoo_steps.py`) — risque nettement plus faible, mais aucun modèle Odoo réel (`sale.order`,
  `account.move`, `stock.picking`…) n'a été rejoué.

**Procédure de vérification recommandée** : `docker compose -f compose.banc.yml up -d` puis
`python scripts/banc_mesure.py --version 16.0` (et 17.0/18.0) contre un flux réel
devis→commande→livraison→facture, en comparant le DOM relevé aux candidats ci-dessus — corriger
la table plutôt que la contourner si un candidat ne matche pas.

### Écarts constatés avec le plan

- `context.odoo_version` posé dans `odoo_session` (par scénario), pas dans `before_all` — voir
  ci-dessus, décision technique documentée dans le code.
- Le lot ne précise pas de sélecteur pour `ligne_x2many_cellule`, `dialogue`,
  `notification_erreur`, `fil_ariane`, `recherche_facette`, `ignorer` : complétés avec les
  conventions DOM les plus documentées d'Odoo, à vérifier sur banc (voir ci-dessus).
- « Tolérance d'arrondi de la devise » : lit `res.currency.rounding` via le champ `currency_id`
  du document quand il existe (convention Odoo répandue mais pas universelle), replie sur 0,01
  sinon — jamais un échec technique pour une tolérance qui n'est qu'un raffinement de précision.
