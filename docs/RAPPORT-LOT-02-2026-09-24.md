Écarts constatés avec le plan :

Corrigés (`f0fecb0`), un test par défaut, échec prouvé sans correctif ; vérifié sur la copie : 31 tables, lignes identiques avant/après, `integrity_check` ok, aucune violation nouvelle.
- Un hook Behave en échec n'a ni step ni message dans le JSON : le message est repris du texte imprimé par Behave (`combined_log`) ; sans lui l'écran dirait « bloqué » sans dire pourquoi.
- `ScenarioVerdict` d'un cas partiellement bloqué : l'axe exécution vaut `blocked` mais le fonctionnel reste `indetermine`, jamais `conforme` (test).

Risques / points à surveiller :
- **Un hook en échec est classé prérequis quel que soit le type d'exception (D1)** : un bug de NOTRE code dans `before_scenario` (par exemple dans la capture de réponse) apparaîtrait aussi `blocked`, pas `retest`. Le message Behave est conservé pour le distinguer.
- `quality_summary` : `blocked` est dans le dénominateur du taux (comme les anciens `technical_error`). C'est un choix de continuité de série ; un prérequis manquant dégrade donc le taux de « tests qui tournent ».
- La migration 19 (`donnee_invalide`) contient la même substitution littérale du nom de table ; elle ne s'exécute plus que sur des bases antérieures à sa version, mais elle porte le même défaut latent.
