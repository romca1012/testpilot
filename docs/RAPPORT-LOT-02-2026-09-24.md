Risques / points à surveiller :
- **Portée de la capture F10** : les codes HTTP ne sont captés que pour `/website/form/…` (Odoo). Ailleurs, un silence reste `indetermine` ; un scénario sans page (RPC seul) ou dont la lecture de page plante garde l'ancien constat (jamais un `indetermine` par défaut de mesure).
- **Borne temporelle** : l'horodatage `t` est posé à la livraison de l'événement Playwright, pas à l'arrivée de la réponse ; un 5xx arrivé juste avant le relevé peut être livré après et compté à tort (sens prudent : `non_conforme`). Les traces sans `t` sont conservées.
- **5xx sur un négatif** : tout 5xx de `/website/form/` du scénario est imputé, y compris sur un autre formulaire de la page (assumé par D12).
- **Cas 99** : le `KeyError: 0` vient d'une équipe de support absente ; possible cause de configuration d'instance plutôt que défaut applicatif (à garder pour le lot 03).
- **Lecture à l'écran** : `indetermine` s'affiche « retest », qui peut suggérer un test cassé alors que c'est un manque d'observabilité (à valider côté UX).
- **Un hook en échec est classé prérequis quel que soit le type d'exception (D1)** : un bug de NOTRE code dans `before_scenario` (par exemple dans la capture de réponse) apparaîtrait aussi `blocked`, pas `retest`. Le message Behave est conservé pour le distinguer.
- `quality_summary` : `blocked` est dans le dénominateur du taux (comme les anciens `technical_error`). C'est un choix de continuité de série ; un prérequis manquant dégrade donc le taux de « tests qui tournent ».
- La migration 19 (`donnee_invalide`) contient la même substitution littérale du nom de table ; elle ne s'exécute plus que sur des bases antérieures à sa version, mais elle porte le même défaut latent.
