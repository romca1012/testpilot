### Ce que le lot change, en clair

Un test « vert » n'a pas toujours la même valeur. Quand la cascade déterministe de `locate_field` / `navigate_menu` /
`click_first_actionable` échoue et qu'un LLM retrouve un élément renommé, ou quand le test ne passe qu'au second essai après un
timeout, le vert cache soit une **régression d'interface**, soit une **instabilité**. Ces signaux étaient tracés, mais
n'atteignaient jamais le verdict. Ils atteignent maintenant l'écran : « **Réussi — à confirmer** », avec la raison.

Ce n'est ni un nouveau statut ni un troisième axe : le statut de lecture reste `passed`, les deux axes restent `success` /
`conforme`. `confiance` **qualifie** ce vert.

### Revue `verdict-reviewer`

1 bloquant, corrigé : `read_selector_tiers` coupait à 200 lignes ; le sidecar reçoit une ligne par champ résolu, nominal compris, donc une résolution adaptative tardive
d'une longue feature disparaissait et le vert passait « nominal ». Corrigé (les lignes adaptatives ne sont jamais tronquées), test qui échoue sur l'ancien code.
À corriger, fait : la note du second essai garde les éléments retrouvés par repli. Vérifié sans problème : deux axes, signal du runtime seulement, garde-fous, migration,
adaptation des deux tests existants (légitime, non affaiblissante).

### Risques / points à surveiller

- **`menus_appris`** : un menu retrouvé par un LLM au run 1 est appris ; au run 2 la cascade le retrouve « nominalement ». La confiance dit « nominale » pour un menu qui
  a pourtant changé. Limite de D5, préexistante à l'apprentissage.
- **Historique** : toutes les exécutions d'avant le lot valent `nominale` par défaut. Ce n'est **pas une mesure** (la confiance n'était pas calculée) ; aucune quatrième valeur
  « inconnue » n'existe (D5 : trois valeurs). Documenté dans la migration.
- Un sidecar dont l'écriture échoue (`except OSError`) ou dont une ligne est illisible ne se distingue pas d'un run sans repli (sens optimiste). Aucune occurrence mesurée.
- La confiance est persistée au niveau de l'**exécution** ; les éléments retrouvés vivent dans le commentaire. Rien par scénario en base.
- Deux scénarios de même nom (« Plan du scénario ») partagent leurs résolutions (sur-signalement, jamais l'inverse) — même limite que les constats.

### Point tranché : le mode strict ne répare jamais (complément à D5, 2026-09-25)

La revue avait relevé qu'une campagne stricte gardait la réparation automatique. **Le porteur a tranché** : elle est désactivée en mode strict, quel que soit le scénario
et le budget de réparation. Justification : l'esprit du mode strict est qu'aucune intervention, humaine ou par modèle, n'a eu lieu entre la génération et le verdict.
L'explication IA reste active (descriptive, sans effet sur le verdict). Consigné au registre (« D5 (complément) »). Test falsifiable : hors strict l'échec déclenche la
boucle de réparation (précondition prouvée, budget par défaut positif), en strict jamais — le test échoue si on retire la garde (vérifié).

### Suggestions hors périmètre
