## Résumé

Six chantiers, tous testés et committés séparément :

1. **`inspect_odoo_view`** — perception RPC d'une vue Odoo (boutons avec leur vraie condition de
   visibilité, barre d'état, champs x2many + sous-champs éditables, champs requis).
2. **`inspect_page_snapshot`** — instantané des éléments interactifs réellement visibles d'une
   page web (rôle, nom accessible, type).
3. **Catalogue groupé par intention** — sous-classement cosmétique (connexion / navigation /
   saisie / action / constat UI / constat serveur) du catalogue de steps montré à l'agent.
4. **Prompt système** — « observer avant de nommer », préférer un constat serveur à un message
   affiché quand c'est possible.
5. **Garde de réparation des assertions** — détecte un scénario supprimé, une assertion `.feature`
   réécrite, une valeur d'`Examples` changée, ou un `@then` dont le CODE a changé — rendu
   vérifiable après coup ce que `repair_prompt.md` demandait déjà en texte.
6. **Réparation guidée par des faits runtime** — vérifié (et désormais prouvé par test)
   que `blocked`/`aucun_constat` n'ouvrent jamais la boucle de réparation automatique ; ajouté les
   paliers de résolution (`field_fallbacks`) comme contexte factuel.

Plus un correctif trouvé en cours de route : `qualify_campaign_pilot.py` nommait chaque dossier
d'essai avec une date codée en dur (2026-09-23), empêchant toute DEUXIÈME campagne de mesure sur
la même version de tourner sans collision — trouvé en essayant de lancer la mesure de clôture.

## Décision arbitrée avec le porteur en cours de lot

Le brief du lot demandait de transmettre la **cause classifiée** (`defect_taxonomy`) au prompt de
réparation. Le code de `repair_agent.py` porte un commentaire citant un incident réel mesuré (cas
6) où donner une conclusion toute faite à l'agent l'a enfermé sur une fausse piste. **Décision,
avec le porteur : ne pas transmettre la cause** — `repair_circuit` (qui doit, lui, décider s'il
ouvre la boucle) la consomme déjà ; c'est un usage différent d'un même signal. Verrouillé par un
test de non-régression (`test_repair_agent_failure_report.py`).

Rapports : `docs/mesures/banc-16.0-2026-09-30-generation-lot09-etape0-baseline.{md,json}` et

**I3/I4 n'ont pas bougé — cause identifiée, pas devinée.** Inspection du détail d'exécution de 10
des 11 cas restés `blocked` (les deux mesures) : **9 sur 10** échouent sur la MÊME erreur —

```
PRÉREQUIS MANQUANT : le compte « banc_manager »/« banc_commercial » n'existe pas sur ce projet
(comptes connus : principal).
```

14 des 16 fichiers de `specs/banc/` écrivent des personas secondaires (« gestionnaire des
achats », « commercial »...) que `scripts/banc_init.sh`/`.ps1` **ne provisionne jamais** comme
comptes du projet (lot 07b-1, `project_account`) — l'agent invente alors un libellé plausible,
`PreconditionNonRemplieError` lève correctement (comportement voulu, D8), et le cas reste
`blocked`. C'est un **trou de configuration du banc**, présent AVANT ce lot et toujours présent
après : aucun des deux tirages ne pouvait montrer d'amélioration sur ces 9 cas, quel que soit ce
que le lot 09 change, puisque le blocage survient **avant** que la perception/le prompt/la
réparation entrent en jeu.

Sur l'échantillon non confondu par ce trou (cas `vente_total`, `droit_suppression`,
`crm_opportunite`, `achat_confirmation`... une fois les comptes déclarés), aucune mesure séparée
n'a pu être faite dans le budget de cette session — voir Suggestions.

## Écarts constatés avec le plan

- Le brief attendait une hausse mesurable d'I3/I4 dans ce lot. Avec ce trou de configuration
  toujours ouvert, la mesure demandée est **structurellement incapable** de le montrer sur ce
  corpus — ce n'est pas un signe que le lot n'a rien amélioré, c'est un signe que l'échantillon
  ne permet pas de le voir. Signalé plutôt qu'arrondi.
- Cause classifiée non transmise au prompt de réparation (voir section dédiée ci-dessus) — écart
  assumé et arbitré avec le porteur, pas un oubli.
- Intention par step : classée par mots-clés du libellé (heuristique), pas un champ tenu à jour à
  la main — cohérent avec le style du dépôt, mais quelques libellés à la frontière (ex. « je
  clique sur l'onglet ») peuvent atterrir dans la mauvaise section. Purement cosmétique, jamais
  bloquant.

## Risques / points à surveiller

- `inspect_odoo_view` : la « visibilité conditionnelle » d'un bouton est le domaine Odoo BRUT
  (`[["state","not in",[...]]]`), pas évalué — l'agent doit savoir lire cette syntaxe (déjà
  documentée dans son prompt via les steps de workflow existants, pas nouveau).
- `diff_feature` compare des scénarios PAR NOM — un scénario renommé ET modifié dans la même
  réparation serait vu comme « supprimé » + « ajouté », jamais comme « modifié ». Limite assumée,
  cohérente avec `blast_radius` qui a la même limite sur les libellés de step.
- Le trou de configuration du banc (comptes `banc_manager`/`banc_commercial`) bloquera TOUTE
  future mesure du lot 04/08/09 sur ce corpus tant qu'il n'est pas comblé.

## Suggestions hors périmètre

- **Déclarer `banc_manager`/`banc_commercial` comme comptes secondaires du projet `banc`**
  (`scripts/banc_init.sh`/`.ps1`, table `project_account`, lot 07b-1) — débloquerait 9 des 15 cas
  du corpus pour une vraie mesure d'I3/I4. Priorité haute : sans ça, aucune mesure future de ce
  corpus n'est interprétable.
- Une fois ce trou comblé, relancer la mesure de clôture de CE lot pour savoir si les 6 chantiers
  ont réellement amélioré I3/I4 sur les cas non confondus — la question reste ouverte.
- `banc_mesure.py` plante sur un caractère `→` à l'affichage final sous Windows (`cp1252`) après
  avoir écrit les rapports — cosmétique (les fichiers sont bons), mais fausse le code de sortie.
- Durcir `write.py` contre un import de nom privé (`_...`) depuis `_base_helpers` — relevé par
  `verdict-reviewer` sur le lot 07e, non traité, toujours valable.
